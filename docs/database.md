# Database

PostgreSQL, accessed through Drizzle ORM. 32 tables. Schema in `packages/database/src/schema.ts`; versioned SQL in `packages/database/migrations/`.

## Driver abstraction

NEXA targets PostgreSQL, full stop. What varies is how the process reaches an engine:

| `DATABASE_DRIVER` | Engine | Use |
| --- | --- | --- |
| `pglite` (default) | Real PostgreSQL compiled to WASM, in-process, persisting to `DATABASE_DIR` | Local development, CI, tests |
| `postgres` | A PostgreSQL server over the wire via `DATABASE_URL` | Production |

Both expose the identical Drizzle surface, so application code never branches on the driver. Migrations are generated once against the Postgres dialect and applied unchanged by either.

The point is that `git clone && npm install && npm run setup` works on any machine with Node — no Docker, no local Postgres, no "ask someone for the connection string". It is the same engine, not a substitute.

## Conventions

**UUID primary keys**, generated by the database with `gen_random_uuid()`. Ids are safe to expose and safe to merge across environments.

**Money is an integer count of minor units** — pesewas, cents — in `bigint` columns. Never a float, never `numeric` for amounts. `bigint` rather than `integer` because the 2.1 billion ceiling is only ~21M GHS, which a real business will pass. Conversion happens only at the presentation edge, via `formatMoney()` / `toMinorUnits()` in `@nexa/config/locale`.

**Every business-owned row carries `business_id`** with `ON DELETE CASCADE`, and an index leading with it. This column is the tenancy boundary.

**Enums come from `@nexa/types`.** The Drizzle `pgEnum`s are built from the same arrays the application imports, so the database and the code cannot drift.

**Timestamps** are `timestamptz`, always UTC. Every table has `created_at`; mutable tables have `updated_at`.

## Table groups

### Identity
`users`, `sessions`, `verification_tokens`

Passwords are scrypt hashes in a versioned format (`scrypt$1$salt$hash`). Sessions store only the SHA-256 digest of an opaque token — the raw token exists only in the cookie, so a database dump does not yield working sessions.

### Tenancy
`businesses`, `business_settings`, `business_members`, `subscriptions`

`business_members` is the authorization root: it carries the role, and its existence is what makes a business visible to a user.

### Customers
`customers`, `customer_tags`, `customer_events`

`customers` carries denormalised rollups recomputed on every related write. `customer_events` is the append-only timeline the customer profile renders.

### Catalogue and inventory
`product_categories`, `products`, `inventory_movements`

`products.quantity` is the current level; `inventory_movements` is the ledger that explains it. Every change — sale, restock, correction, damage, return, cancellation — writes a movement with the resulting balance, so any quantity can be traced to its causes.

### Sales
`orders`, `order_items`, `invoices`, `invoice_items`, `payments`

Line items snapshot the product **name and cost at the time of sale**. Renaming or repricing a product must not rewrite history. `payments` can reference an order or an invoice, which is what lets both share one settlement path.

### Expenses
`expense_categories`, `expenses`

Note that stock purchases are *not* expenses here. Cost of goods is already captured through `order_items.unit_cost_minor`; recording restocks as expenses too would double-count them and understate profit. Restocks live in `inventory_movements`.

### Work
`tasks`, `appointments`

### Signals
`activity_events`, `notifications`, `campaigns`, `message_outbox`

`activity_events.dedupe_key` has a partial unique index, making repeated agent scans idempotent. `message_outbox` records every outbound message with a `simulated` flag, so the product can say "prepared, not delivered" rather than implying a send that did not happen.

### AI
`ai_conversations`, `ai_messages`, `ai_actions`, `ai_action_approvals`

`ai_actions` is the approval queue. A consequential tool call lands here as `proposed` with its validated payload and a human-readable preview; execution happens only after a decision is recorded in `ai_action_approvals`.

### Audit and analytics
`audit_logs`, `usage_events`

`audit_logs` is append-only and covers user *and* AI actions, including the payload of anything the AI executed. `usage_events` carries product analytics (activation, engagement, retention) on a closed vocabulary so dashboards stay stable.

## Indexing

Every tenant table leads with `business_id`. Beyond that:

- `orders (business_id, occurred_at)` — the range scan behind every revenue figure
- `orders (customer_id, occurred_at)` — customer timelines
- `invoices (business_id, due_date)` — overdue detection
- `customers (business_id, last_purchase_at)` — lapsed-customer segmentation
- `order_items (product_id)` — product performance and sales velocity
- Partial unique indexes for nullable natural keys: customer email and product SKU are unique *within a business, when present*

## Changing the schema

```bash
# 1. edit packages/database/src/schema.ts
npm run generate -w @nexa/database   # emits a new SQL migration
npm run db:push                      # applies it
```

Migrations are checked in. `drizzle-kit push` (schema diffing without a migration file) is deliberately not wired up — production schema changes should be reviewable artefacts.
